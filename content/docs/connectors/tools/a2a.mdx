# A2A (Agent-to-Agent)

A2A is a protocol that lets one agent call another agent as a tool. The coordinator receives a user message, decides a subtask needs to be handled by a specialist, calls the sub-agent with a query, receives the response, and incorporates it into its own answer.

From the model's perspective, calling a sub-agent looks identical to calling any other tool — it sends a request with arguments and receives a result.

## When to use A2A

A2A is the right choice when a subtask itself requires LLM reasoning. For example:

- A coordinator agent routes incoming questions to a legal specialist agent or a technical specialist agent, each with their own knowledge base and system prompt
- A research coordinator delegates summarization of individual documents to a sub-agent, then synthesizes the summaries
- A translation pipeline sends content to a specialized translation agent before the main agent processes the result

**Compare to MCP:** Use MCP for deterministic, code-defined tools (database queries, API calls, file operations). Use A2A when the work being delegated needs language understanding and reasoning.

## Setting up A2A

### Configure the sub-agent

The target agent is a normal OpenAgent Store configured however you want — its own model, prompt, knowledge base, and tools. It doesn't need any special configuration to act as an A2A sub-agent beyond being accessible at an A2A endpoint.

### Configure the coordinator

1. Go to **Providers → Add Provider**, category **Agent**, type **A2A**
2. Set **Provider URL** to the sub-agent's A2A endpoint
3. Save the provider
4. Edit the coordinator Store → set **Agent Provider** to this A2A provider
5. Save

During conversations with the coordinator Store, the model can invoke the sub-agent as a tool. The sub-agent's response is returned as the tool result.

<Callout type="info">
  A Store supports one Agent Provider at a time. If you need a coordinator that routes to multiple sub-agents, the cleanest approach is to create an MCP server that wraps multiple A2A endpoints — each sub-agent becomes a separately named tool on the MCP server.
</Callout>

## Designing multi-agent systems

A few patterns that work well:

**Triage + specialist routing** — a coordinator with a broad system prompt receives all messages. Its only job is to call the right specialist agent. Each specialist has a narrowly focused prompt and a domain-specific knowledge base. The coordinator synthesizes their responses if needed.

**Pipeline** — Agent A processes input and produces structured output. Its output becomes the input to Agent B. Useful for multi-step transformations where each step needs separate reasoning.

**Review** — Agent A generates a response. Agent B (the reviewer) receives Agent A's output as its input and checks it against criteria. The coordinator decides whether to return Agent A's output or request a revision.

## Observability

Tool calls to sub-agents are recorded in the parent Message's `toolCalls` field, just like MCP tool calls. You can see the query sent to the sub-agent and the response received. The sub-agent's own Chat and Message records are created separately under its own Store context.

This means you can trace a conversation from the coordinator's perspective (what it asked sub-agents, what they returned) and also drill into each sub-agent's Chat to see how it arrived at its answer.
